# AGENTS.md

This is the instruction file for every AI coding tool on the team (Claude Code, Antigravity, Copilot, etc.). `CLAUDE.md` only imports this file. Add new rules here, not to `CLAUDE.md`, `GEMINI.md`, or any other tool-specific file.

## Project
A social site for gamers: share posts and clips, review and discover games, and find people to play with.

## Stack
Frontend and server code: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS 4
Database, auth, and file storage: Supabase (`@supabase/supabase-js`, `@supabase/ssr`)
Hosting: Vercel
Node.js: 24 LTS

## Commands
Install: npm install
Run locally: npm run dev (http://localhost:3000)
Build: npm run build
Lint: npm run lint
Database types: npm run db:types (needs a one-time `npx supabase login`)
Test: no test runner yet. Ask before adding one.

## Rules
- One story per PR. Keep changes small.
- Once a test runner exists, write or update tests for every change. Until then, say in the PR how you checked the change.
- Never commit secrets, `.env`, or `.env*.local` files. `.env.example` (placeholder values only) is committed.
- Ask before adding a new dependency.
- Don't guess at existing Supabase tables, columns, or storage buckets. Check `lib/database.types.ts` (exact columns) and `docs/database/schema.dbml` (the diagram and design notes), or ask. If a story needs a new table, say so and write the SQL (with RLS, grants, and policies) for a teammate to review and run.
- Before asking for review, run `npm run lint`, `npx tsc --noEmit`, and `npm run build`, and make sure all three pass. Then use the feature in the running app: open the page that renders it, and try the signed-out state and the failure cases. Passing checks only cover code that something imports, so a component that no page renders hasn't been tested. In the PR, list what you checked and what you couldn't check.
- Every source file needs a `.ts` or `.tsx` extension, and its path must match where it's imported from. Tools skip files they don't recognize, so a green lint, build, or Vercel check doesn't prove a file was checked.
- Don't open a PR that only contains stubs, placeholder values (such as a fake ID), or comments like "logic here". Open a draft PR or an issue instead.
- Change only the files your story needs. If you find a problem in a feature someone else owns, especially auth, the database, or migrations, tell its owner or open an issue instead of fixing it in your PR. Changes outside your story, such as auth fixes or layout edits, go in their own PR.
- Sample data, fake profiles, and preview switches (such as `?preview=`) may only work when `process.env.NODE_ENV === 'development'` or `process.env.VERCEL_ENV === 'preview'`. In production, missing data shows an empty state or `notFound()`, never sample data.

## Working with AI agents
- AI agents never commit, push, merge, open, approve, comment on, or close PRs or issues, deploy, or change Supabase, Vercel, or GitHub settings, unless a team member explicitly asks for that action. Approval for one action doesn't cover the next one.
- Don't add AI co-author or "generated by" lines to commits, PR descriptions, or issues. Some tools add them by default, so turn that off in the tool's own settings too.
- Stage files by exact path, and check `git diff --cached --name-only` before committing.
- Only stop processes you started, by their process ID or port. Never use broad commands that match by name, like `pkill -f next`.
- This repository is public. Don't describe security weaknesses (how to get around a permission check, an unvalidated input, a missing check) in docs, code comments, commit messages, PRs, or issues. Tell the feature owner privately, and describe the fix in neutral terms.

## Database
- The schema lives in `supabase/migrations/`. Every schema change is a NEW migration file named `<YYYYMMDDHHMMSS>_<what_it_does>.sql`. Never edit a migration that has already been run on Supabase.
- Migrations are reviewed in a PR, then run once by hand in the Supabase SQL Editor after merging. Say in the PR when it has been run.
- After a migration has been run, regenerate the types with `npm run db:types` and commit `lib/database.types.ts`. Also update `docs/database/schema.dbml` to match.
- Never edit `lib/database.types.ts` by hand. It is generated from the live database.
- The Supabase clients in `lib/supabase/` are typed with `Database`, so table and column names are checked by TypeScript. Don't cast query results to `any`. For component props, use the generated helpers: `Tables<'posts'>` (a row), `TablesInsert<'posts'>`, `TablesUpdate<'posts'>`.
- The types say which columns exist, not which ones a user may write. Grants and RLS in the migration decide that (e.g. `posts.upvote_count` exists but users can never set it).
- When a query embeds a related table and the tables are connected in more than one way, name the foreign key, e.g. `profiles!posts_author_id_fkey(username)`. `posts` reaches `profiles` both directly and through `post_votes`. TypeScript doesn't catch an ambiguous embed. The database rejects it when the query runs (error `PGRST201`), so run every new query against a real database before review.

## Next.js 16
Your training data is likely out of date. Follow these:
- Use `proxy.ts` at the project root (next to `app/`), not `middleware.ts`. Export the function as `proxy`, not `middleware`, and don't add a `runtime` export.
- In server code (pages, layouts, Route Handlers, Server Actions, `generateMetadata`), `params`, `searchParams`, `cookies()`, and `headers()` are Promises. Always `await` them. Client Components can't be `async`: unwrap those props with React's `use()`, or use the `useParams()` and `useSearchParams()` hooks.
- A file marked `'use client'`, and everything it imports, must not use server-only code: `lib/supabase/server.ts`, `next/headers`, the secret key, or any file that imports them, even indirectly. Put helpers that both sides need (formatting, sorting, threading) in their own file with no server imports. Start every server-only module with `import 'server-only'`, so a wrong import fails with a clear error.
- Anything rendered on both the server and the browser must render the same text in both. Don't format dates, times, or numbers with the reader's locale or time zone (`toLocaleString()`, `toLocaleDateString()`, `toLocaleTimeString()`, `Intl` without fixed options). Use a fixed locale and time zone (e.g. `new Intl.DateTimeFormat('en-US', { dateStyle: 'medium', timeZone: 'UTC' })`), or format only after the component mounts. `suppressHydrationWarning` doesn't fix this.

## Supabase
- Use `@supabase/ssr` (`createBrowserClient`, `createServerClient`). Never use `@supabase/auth-helpers-nextjs`.
- In `createServerClient`, use only the `getAll` and `setAll` cookie methods, never `get`, `set`, or `remove`. `setAll(cookiesToSet, headers)` gets cache headers as its second argument. In `proxy.ts`, set them on the response, or Vercel's CDN can serve one user's session to another. Create a new server client for every request.
- Env vars are `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (`sb_publishable_...`), in both client and server code. The secret key (`sb_secret_...`) goes only in `SUPABASE_SECRET_KEY`, and is read only in a file that starts with `import 'server-only'` (built into Next.js, no install needed). Never put a `NEXT_PUBLIC_` prefix on a secret.
- Don't use the legacy key names `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_ANON_KEY`, or `SUPABASE_SERVICE_ROLE_KEY`, or any key that starts with `eyJ`. The `anon` and `authenticated` Postgres roles in grants and policies are still correct.
- To check who is logged in on the server, use `supabase.auth.getClaims()`. The user id is `data.claims.sub`. Use `supabase.auth.getUser()` instead for sensitive actions (account settings, deleting data) that must reject a session that was signed out or banned. Never trust `getSession()` in server code. `proxy.ts` only refreshes the session, so check auth in every page, Server Action, and Route Handler that needs it.
- Treat every redirect destination that comes from the URL (`next`, `redirect`, `returnTo`) as untrusted, in Route Handlers, Server Actions, and client `router.push` alike. Use it only if it is a path on this site: it starts with exactly one `/`, and not `//` or `/\`. Otherwise redirect to a safe default such as `/`.
- New tables in `public` are not exposed to the API automatically. Each one needs, in the same migration: RLS enabled, `grant`s, and policies. Grant each role only what it needs: `authenticated` gets the operations the app uses, `anon` gets only `select` on data signed-out visitors may see (often nothing), and `service_role` gets what server code using the secret key needs. Write one policy per operation (`for select`, `insert`, `update`, `delete`), and never add `using (true)` just to have a policy. Views also need grants, and must use `with (security_invoker = true)`.
- Storage (clips, images): `storage.objects` already has RLS on and needs no grants, but nothing can be uploaded until there are policies on `storage.objects` for that `bucket_id`. Uploading needs `insert`. Downloading or creating signed URLs needs `select`. Deleting needs `select` and `delete`. Overwriting needs `select`, `insert`, and `update`. Never alter the `storage` schema with SQL.

## Things you got wrong before
Add a short line every time an agent makes a mistake that could happen again.
- (Nov 2026) A client component imported a helper file that also imported the server Supabase client. The build passed only because no page rendered the component, and it broke the moment a page did. See the server/client rule under Next.js 16.
- (Nov 2026) Files were committed without a `.ts`/`.tsx` extension. Lint, TypeScript, and the build skipped them, and the Vercel check still showed success.
- (Nov 2026) A PR contained only placeholder code with a fake ID, and no real implementation.
- (Nov 2026) Dates were formatted with the reader's locale and time zone, which caused a hydration error for readers in other locales.
- (Nov 2026) A query embedding `profiles` from `posts` passed TypeScript but failed on the live database, because the join was ambiguous. Fixed by naming `posts_author_id_fkey`.
- (Nov 2026) A `git add` of a renamed file failed, and the commit went ahead with the wrong contents. It was caught and fixed before pushing.
- (Nov 2026) A broad `pkill` command was used to stop a dev server, and it could have stopped unrelated servers on the same machine.
- (Nov 2026) A PR mixed unrelated auth and layout changes into a feature PR without listing them in its description.
- (Nov 2026) AI co-author lines were added to commits after the team decided not to use them. Existing commits stay as they are, and history is not rewritten.
- (Nov 2026) A draft doc described a security weakness in detail. It was removed before pushing.
